### 운영 Supabase와 소스 마이그레이션

2026-10-09 읽기 전용 조회에서 운영 `public` 테이블은 `teams`, `players`, `matches` 세 개이고 모두 RLS가 켜져 있다. 각 테이블에 `SELECT/INSERT/UPDATE/DELETE` 사용자 소유 정책이 있으며 `(user_id = auth.uid())`를 사용한다. `updated_at`은 세 테이블에 존재하고 UPDATE 트리거가 있다. `competition_states`는 없다. 운영 컬럼은 주로 `shortName`, `teamId`, `teamIds`, `matchDay`, `appearances`, `events`, `externalPlayerId`(jsonb), `photoUrl`처럼 camelCase다. 경기의 `competition_type`, `competition_stage`, `competition_pairing_id`, `competition_series_game`, `competition_assignment`는 없다. 운영 프로젝트의 Supabase 마이그레이션 이력 조회는 빈 목록을 반환했다. 소스 SQL에는 `competition_states`, snake_case 선수·대회 컬럼이 있으므로 **소스 마이그레이션은 운영 스키마의 증거가 아니다**. `.env.local`의 URL 호스트는 조회한 프로젝트와 일치한다. 실제 배포 설정도 같은 프로젝트인지 별도 확인이 필요하다. API 키 값은 출력하거나 사용하지 않았다.

## B. 발견한 문제

각 항목의 `재현`은 전체 브라우저 E2E가 아니라 격리 테스트인지 함께 표시한다. 운영 DB 불일치는 스키마 조회로 확인했으나 실제 계정으로 동기화 요청은 보내지 않았다.

### P0-1. 운영 스키마와 동기화 계약 불일치

- **확인**: 운영 스키마 읽기 전용 조회 + 정적 비교. `syncNow`는 없는 `competition_states`를 항상 SELECT하므로 한 오류만 나도 병합을 중단한다 (`src/lib/sync.ts:60-61`). 클라우드 직렬화는 선수에게 `external_player_id`/`photo_url`, 경기에게 `competition_*`를 생성하지만 운영 테이블은 다른 컬럼을 가진다 (`src/lib/cloudMatch.ts:4-20`; 운영 조회 결과). `supabase/migrations/20260910120000_add_competitions.sql:1-19` 등 소스 SQL은 적용 상태를 보증하지 않는다.
- **조건·영향·SOT**: 연결된 프로젝트를 사용하는 모든 로그인 동기화. 로컬 `football-tracker-v1`은 우선 보존되지만 클라우드 백업·새 기기 복원이 실패할 수 있다. 클라우드와 로컬의 계약 자체가 맞지 않는다.
- **기존 검증 / 설계 / 회귀 / 단계**: `tests/competition.test.cjs:117-118`은 문자열 존재만 검사해 실제 스키마를 검증하지 않는다. 3차에서 운영 스키마를 기준으로 읽기 전용 타입 생성·컬럼 매핑·격리 DB 계약 테스트를 먼저 만들고, 데이터 백업 후 호환성 마이그레이션 또는 클라이언트 변환을 설계한다. RLS·기존 행·구버전 클라이언트 회귀 위험 높음.

### P0-2. 확정 경기 저장 뒤 오래된 일반 수정 스냅샷이 원본을 덮을 수 있음

- **재현**: 모델 기반 격리 테스트 실패 (`tests/audit/phase1-risk-repros.test.cjs:18-27`): 확정 경기 스냅샷 뒤 기존 상태에서 만든 일반 수정 스냅샷을 큐에 넣으면 최종 원본의 경기 목록이 빈 배열이다. 전체 React 화면 동시 조작 재현은 미실시.
- **원인·조건·영향·SOT**: `saveMatchDurably`는 `snapshotRef.current`에서 전체 `next`를 구성하고 `await persistLocal(next)` 후 React 상태에 경기를 넣는다 (`src/store.tsx:161-195`). 대기 중 다른 `update`가 경기 없는 React 상태에서 스냅샷을 만들어 나중에 저장하면 저장 큐는 **순서만** 지킬 뿐 내용의 최신성을 보장하지 않는다 (`src/store.tsx:149-157`, `src/lib/persistenceQueue.ts:1-13`). UI에는 경기가 보이다가 재시작 후 사라질 수 있다. 원본은 `football-tracker-v1`.
- **기존 검증 / 설계 / 회귀 / 단계**: `tests/p0-durability.test.cjs:202-215`는 먼저 큐에 들어온 draft와 final의 순서만 검증한다. 2차에서 모든 로컬 변경을 단일 직렬 트랜잭션으로 묶고, 확정 경기의 리비전을 올린 뒤 최신 스냅샷으로 원본 저장과 UI 승인을 연결한다. 기존 편집·실패 복구·draft 잠금 회귀 위험 높음.

### P0-3. 클라우드 병합이 새 로컬 경기 저장을 덮을 수 있음

- **재현**: 실제 `SyncManager`를 격리 저장소·가짜 클라우드로 실행. SELECT 대기 중 로컬 원본에 경기 M을 저장한 뒤 병합을 재개하자 M이 사라짐 (`tests/audit/phase1-sync-risk-repros.test.cjs:46-57`).
- **원인·조건·영향·SOT**: sync는 원본을 한 번 읽고 (`src/lib/sync.ts:55`), 네 테이블을 기다린 뒤 이전 `local`로 병합하여 `LocalRepository.saveAppState(merged)`를 **Store 저장 큐 밖에서** 호출한다 (`src/lib/sync.ts:60-88`). 새 로컬 변경·UI 상태·클라우드 원본이 벌어질 수 있다. 이후 Store의 저장이 우연히 회복시킬 수도 있지만 보장되지 않는다.
- **기존 검증 / 설계 / 회귀 / 단계**: 기존 sync 테스트는 최신 원본과 원격 행의 우선순위만 다룬다. 2차 단일 저장 트랜잭션 인터페이스를 만든 후 3차에서 병합 전후 원본 리비전 재검사 및 재병합/재시도를 도입한다. 타 기기 동기화·로그인 시작 회귀 위험 높음.

### P0-4. 다른 기기에서 삭제한 원격 경기가 다시 업로드됨

- **재현**: 격리된 `SyncManager`에서 로컬 경기 M, 원격 빈 목록, 대기 큐 없음으로 동기화하면 로컬 M이 남음 (`tests/audit/phase1-sync-risk-repros.test.cjs:37-44`). 코드상 그 다음 원격에 없는 로컬 행은 upsert 큐에 추가된다 (`src/lib/sync.ts:89-102`).
- **원인·조건·영향·SOT**: 병합이 단순 ID 합집합이고 삭제 tombstone/원격 세대 정보가 없다 (`src/lib/sync.ts:64-85`). 동기화된 두 기기 중 하나가 삭제하면 다른 기기가 삭제를 되돌릴 수 있다. 클라우드 및 로컬 경기 원본 모두 영향.
- **기존 검증 / 설계 / 회귀 / 단계**: 다기기 삭제 충돌 테스트 없음. 3차에서 계정별 삭제 이력·서버 개정값·충돌 정책과 멱등 재시도를 정의한다. 기존 로컬 미동기화 행 보존과 구분해야 하므로 회귀 위험 높음.

### P0-5. 빈 새 기기의 첫 클라우드 복원 실패

- **재현**: 격리된 `SyncManager`에서 로컬 원본 없음, 원격 경기 있음으로 실행 시 `status: error` (`tests/audit/phase1-sync-risk-repros.test.cjs:59-67`).
- **원인·조건·영향·SOT**: `getAppState()`가 `null`이면 원격 SELECT 전에 반환한다 (`src/lib/sync.ts:55`). 최초 로그인 기기의 클라우드 복원 경로가 없다. 운영 스키마 P0-1이 해결돼도 이 조건은 별개다.
- **기존 검증 / 설계 / 회귀 / 단계**: 기존 테스트는 로컬 원본이 있는 경우만 점검. 3차에서 빈 기기 부트스트랩과 계정 소유 확인, 사용자가 가진 로컬 데이터와의 합치기 정책을 분리한다. 첫 로그인·계정 전환 회귀 위험 높음.

### P0-6. 클라우드 큐와 메타데이터의 원자성 및 중복 실행이 보장되지 않음

- **확인**: 정적 분석. `queueOperation`은 기존 큐를 읽은 다음 별도 트랜잭션에서 삭제·추가하고, 다시 별도 트랜잭션에서 메타데이터를 쓴다 (`src/lib/sync.ts:33-40`). `syncNow`에 실행 중 잠금이 없고, 각 실행이 큐 스냅샷을 기준으로 업로드 후 ID로 삭제한다 (`src/lib/sync.ts:48-107`).
- **조건·영향·SOT**: 빠른 연속 변경, 온라인 이벤트, 재시도 타이머, 업로드 지연이 겹칠 때 최신 큐 항목의 누락·중복 업로드·잘못된 워터마크가 가능하다. 정확한 손실 순서는 아직 타이밍 테스트로 확인하지 못해 **가능성만 존재**로 분류한다. IDB 큐/메타데이터가 SOT 역할을 한다.
- **기존 검증 / 설계 / 회귀 / 단계**: 동일 ID 연속 큐잉과 동시 `syncNow` 시험 없음. 3차에서 단일 sync 실행, 계정·엔티티별 직렬화, 큐와 워터마크의 한 트랜잭션 커밋, 업로드 완료 시 항목 세대 확인을 설계한다. 오프라인 재시도 회귀 위험 높음.

### P1-4. 논리 경기 슬롯 중복이 저장 검증을 통과

- **재현**: 같은 팀·시즌·MD의 서로 다른 ID 경기 2개에 `validateState`가 `true` 반환 (`tests/audit/phase1-risk-repros.test.cjs:56-61`). `auditDataIntegrity`는 중복을 오류로 표시한다 (`src/engine/integrity.ts:40-68`).
- **조건·원인·영향·SOT**: 동일 슬롯 중복 Import 또는 동시 저장. 저장 검증은 ID 유일성만 검사한다 (`src/lib/validation.ts:37-44`); `saveMatchDurably`도 신규 경기의 슬롯을 재확인하지 않는다 (`src/store.tsx:161-178`). 대회 진행, 통계, 상금/수상 결과가 이중 계산될 수 있다. SOT는 원본 `matches`.
- **기존 검증 / 설계 / 회귀 / 단계**: 무결성 진단과 대회 개별 테스트는 있으나 저장 차단 테스트 없음. 4차 기록 시 슬롯 경쟁 검사, 5차 Import/수정/저장 전 공통 불변조건을 설계한다. 과거 중복 데이터의 읽기 호환성 회귀 위험 높음.

### P1-5. 시즌 조합 수상자가 표시 지표와 불일치

- **재현**: 실제 `seasonRecap`에 적격 트리오 A(270분, G+A 0), B(180분, G+A 2)를 주면 A가 `Best Attack Trio`로 선정됨. 기대 수상자는 B (`tests/audit/phase1-risk-repros.test.cjs:63-76`).
- **원인·조건·영향·SOT**: `seasonRecap`은 모든 조합에서 `combinationStats(...).find(eligible)`를 쓴다 (`src/engine/seasonInsights.ts:145-164`). `combinationStats`의 정렬은 적격 여부 다음 **함께 뛴 시간, 득실차**이고 수상 문구의 G+A·평균 평점·GA/90·클린시트와 다르다 (`src/engine/analytics.ts:101-121`). Attack뿐 아니라 Midfield, CB Pair, Back Four, Duo에도 같은 구조적 위험이 있다. SOT는 `matches`, 수상은 파생 결과.
- **기존 검증 / 설계 / 회귀 / 단계**: 기존 통계 테스트는 조합 수치 위주이며 수상자와 표시 수치의 최대/최소 일치는 확인하지 않는다. 6차에서 부문별 평가 함수·동률 규칙을 명시하고 화면과 수상이 같은 정렬을 사용하게 한다. 과거 수상 표시 변화 위험 높음; 원본 기록은 변경하지 않는다.

### P1-6. React updater 내부 검증 예외가 UI 호출부의 catch와 분리됨

- **확인**: 정적 분석. `addPlayer`, `updatePlayer`, `importPlayers`는 `setSnapshot` updater에 검증·변환을 넣고 즉시 반환한다 (`src/store.tsx:149-159,240-263`). 호출부는 동기 `try/catch`에서 `onReplace` 등 후속 이동을 수행한다 (`src/screens/NewPlayerScreen.tsx:47`, `src/screens/SquadImportScreen.tsx:63-68`). React가 updater를 나중에 실행하면 예외가 해당 catch로 전달되지 않는다. React 실행 시점에 따른 실제 화면 재현은 미실시.
- **조건·영향·SOT / 기존 검증 / 설계 / 회귀 / 단계**: 정원 초과·잘못된 Import에 사용자 오류가 누락되고 UI·저장소 불일치가 가능하다. SOT는 React 상태와 원본 저장소. 기존 정원 테스트는 순수 검사 결과를 검증하나 호출부의 비동기 예외 전달은 확인하지 않는다. 2차에서 updater를 순수 계산으로 제한하고 실패 가능한 사전 검증을 명시적 트랜잭션 API 결과로 반환한다. 5차 등록/수정/Import 검증을 통합한다. 입력 UX 회귀 위험 중간.

### P2-1. 동일 길이의 배열 제자리 변경에서 대회 범위 캐시가 낡음

- **재현**: `matches` 배열의 한 원소를 리그에서 컵으로 제자리 교체해도 리그 조회가 이전 행을 반환 (`tests/audit/phase1-risk-repros.test.cjs:48-54`). 현재 Store의 표준 변경은 새 배열을 만들어 일반 사용자 경로에서는 이 반례가 바로 발생하지 않는다.
- **조건·원인·영향·SOT / 기존 검증 / 설계 / 회귀 / 단계**: 외부 모듈이나 향후 코드가 배열을 제자리 수정하면 `competitionMatches` 캐시가 배열 참조와 길이만 확인한다 (`src/engine/competition.ts:15-25`). 파생 리그/컵 화면이 낡을 수 있다. 7차에서 입력 불변성 계약을 검사하고 필요 시 리비전 키를 사용한다. 기존 캐시 테스트는 새 배열 교체 경로를 검증. 원본 `matches`의 불변성 회귀 위험 중간.

### P2-2. 계산 비용·초기 번들 후보

- **확인**: 정적 분석 + 합성 데이터 측정. `combinationStats`는 경기별 선수 조합 생성과 겹치는 구간·평점을 계산한다 (`src/engine/analytics.ts:61,73-121`); `seasonRecap`은 선수별 시즌 통계와 조합 종류마다 이를 다시 호출한다 (`src/engine/seasonInsights.ts:140-166`). `recordsLeaderboards`의 선택된 조합 9개 미리보기는 60경기·22선수 합성 데이터에서 cold 61.25 ms, repeat 0.03 ms (`node tests/v249-performance.bench.cjs --selected`). 실제 기기 성능 수치로 일반화할 수 없다. 빌드 JS 907.65 kB는 초기 로딩 측정 후보.
- **이미 있는 보호 / 설계 / 회귀 / 단계**: Global Ranking은 `WeakMap`과 REV 키 (`src/engine/stats.ts:267-303`), Rating은 timeline 캐시 (`src/engine/rating.ts:177-178`, `src/engine/timeline.ts:81-116`), 대회는 revision selector와 `useMemo` (`src/engine/competitionSelectors.ts:20-102`, `src/screens/CompetitionScreen.tsx:78-80`)를 사용한다. 7차에서 실제 사용자 데이터 크기와 저사양 기기 계측 후 중복 호출만 제거한다. 캐시 변경은 수상·평점 정확성을 먼저 고정한 뒤 수행. 결과 오류 회귀 위험 중간.

## C. 데이터 안전성

- **로컬 원본**: `football-tracker-v1`의 저장 전 검증·직렬화, 동기 `localStorage.setItem`·read-back 확인은 구현·기존 테스트로 입증된다 (`src/lib/repository.ts:104-138`, `tests/p0-durability.test.cjs`). IndexedDB는 비동기 최선 노력 미러라 `mirrorSaved: false`가 정상 결과다. 저장 중 브라우저 종료는 마지막 성공한 원본을 우선 읽는다. 원본이 없거나 손상되면 IndexedDB, `football-tracker-v1-backup`, 긴급 스냅샷 1~5, 레거시 키 순으로 복구한다 (`src/lib/repository.ts:61-101`). 다만 최근 작업 전체가 보존된다는 보장은 P0-2/P0-3 때문에 없다.
- **용량·백업**: quota 시 유효한 원본이 있으면 레거시 백업/긴급 사본을 지우고 1회 재시도한다 (`src/lib/repository.ts:50-57,118-127`). 이 선택은 주 저장 성공률을 높이는 대신 로컬 복구 사본을 없앨 수 있다. Import 전에 `football-tracker-v1-backup`을 쓰지만 동일 키의 기존 백업을 덮는다 (`src/lib/repository.ts:45-49`). JSON Export는 저장소 전체 `AppState`를 직렬화한다 (`src/lib/repository.ts:142-149`); 저장 대기 중이면 최신 UI보다 늦을 수 있고, 다운로드 완료·파일 내용 재검사는 하지 않는다 (`src/screens/DataManagementScreen.tsx:11-23`). 실제 브라우저 파일을 보지 않았으므로 **백업 완료로 간주할 수 없다**.
- **Import**: 파싱·형식 검증 뒤 사전 백업, 큐 epoch 차단, 원본 저장, React 교체 순서는 구현되어 있다 (`src/lib/importTransaction.ts:35-47`). 이 경로는 일반 갱신과 완전히 같은 직렬 상태 트랜잭션이 아니고, 운영 복원 시험은 하지 않았다. `validateState`가 통과한 구조에도 중복 논리 슬롯이 남을 수 있다.
- **클라우드**: 운영 스키마 불일치로 현재 연결 프로젝트의 정상 동기화는 검증되지 않았으며 정적 경로상 실패한다. 로컬 원본은 우선 보존되지만 데이터가 클라우드에 안전하게 올라갔다고 주장할 수 없다. 소유자 RLS는 운영 스키마에서 확인했으나 계정 전환 시 `lastSyncedUserId`가 설정된 경우의 가드 (`src/lib/sync.ts:56-58`)만 코드로 확인했다. 최초 성공 전에 계정을 바꾸는 경우, 반복 sync 멱등성, 중간 업로드 실패 복구는 다기기 E2E로 확인하지 못했다.
- **수정 전 사용자 백업 절차**: 해당 브라우저에서 Data Management → Export Data를 누르고, 실제 다운로드된 JSON을 별도 위치 두 곳에 복사한다. 파일을 텍스트로 열어 `teams`, `players`, `matches` 배열과 예상 경기 수·최근 경기 ID가 있는지 확인한다. 브라우저 저장소를 지우거나 Import를 실행하지 않는다. 3차 전에 운영 Supabase의 프로젝트 식별자, 읽기 전용 스키마·행 수, DB 백업/복원 수단도 확인한다. 이 감사에서는 실제 사용자 백업을 수행하지 않았다.

## D. 계산·대회 정확성

REV13 계수는 변경하지 않았고, `tests/v253-rev13.test.cjs` 등 기존 테스트가 평점·MOM·랭킹 전파를 통과했다. `timeline`은 이벤트와 추가시간의 최대 시점을 계산하므로 90분 뒤 이벤트를 일률적으로 제거하지 않는다 (`src/engine/timeline.ts:81-116`). 출전 구간 기반 통계는 `tests/analytics.test.cjs`, `tests/position-timeline.test.cjs` 등에서 검증된다. 이는 모든 화면의 수치 동일성을 독립 검산했다는 뜻은 아니다.

리그는 기록된 슬롯으로 진행을 판단하고 (`src/engine/competition.ts:62-67`), 컵·챔피언스의 과거 경기 수정/삭제는 후속 라운드가 불가능해지는 변경을 막는다 (`src/engine/competition.ts:470-499`). 시즌 완료 표식도 완료 조건이 깨지면 제거한다. 기존 `competition*.test.cjs` 및 순위·시즌 테스트는 통과했다. **저장 입구에서 중복 슬롯을 막지 않는 문제 P1-4**는 이 계산들이 잘못된 원본을 받아들일 수 있음을 뜻한다. 수상은 P1-5의 실제 반례가 있다. Best XI·MOM의 다른 계산 불일치는 이번 조사에서 재현하지 못했고, 화면별 모든 필터 조합과 부동소수점 경계는 별도 속성 테스트가 필요하다.

## E. 성능·캐시

현재 Rating·Global Ranking·Best XI·대회 selector·화면 `useMemo`에는 실제 캐시가 있다. Store가 새 경기/선수 배열을 만드는 정상 경로에서는 주요 WeakMap 캐시가 무효화된다. `competitionMatches`만 동일 길이 제자리 수정 반례를 확인했고, 현재 사용자 UI에서 그 제자리 수정이 발생한다고 확인하지는 못했다. 조합 통계는 비용이 큰 후보이나 위 61.25 ms는 합성 입력 1회 계측값이다. 초기 JS 907.65 kB는 청크 경고를 발생시킨다. 7차에서 실제 사용 데이터 크기·브라우저 시간·메모리를 먼저 계측하고, 정확성을 고정한 뒤 호출 공유 또는 화면 지연 로딩을 적용한다.

## 감사용 파일과 실행법

- `tests/audit/phase1-risk-repros.test.cjs`: 6개 기대 실패. 저장 스냅샷 반례는 큐·상태의 **모델 재현**, draft/라인업/캐시/검증/수상은 실제 순수 함수 실행.
- `tests/audit/phase1-sync-risk-repros.test.cjs`: 3개 기대 실패. 실제 `SyncManager`를 격리 로컬 저장소·가짜 클라우드와 실행.

`node --test tests/audit/phase1-risk-repros.test.cjs` 및 `node --test tests/audit/phase1-sync-risk-repros.test.cjs`로 각각 실행한다. 두 명령의 비영(非零) 종료 코드는 발견된 결함의 예상 결과다. `npm test`의 `tests/*.test.cjs` 패턴에는 포함되지 않는다. 사용자 데이터, 운영 DB, 제품 소스 파일은 이 감사에서 변경하지 않았다.
