## Interpretation

Latest Changes and League History show useful reductions in the final run. Default News is noisy: the primary three-sample three-season median is slower; a separate five-pair confirmation produces the opposite result. We do not claim a dependable general News speedup from these wall-clock samples. The confirmation retained identical full results: [raw confirmation](v2.6.4-news-confirmation.json).

- 1 season News confirmation (5 pairs): cold 773.05 -> 602.24, warm 19.40 -> 18.56, edit 523.63 -> 408.85, delete 316.53 -> 354.37 ms.
- 3 season News confirmation (5 pairs): cold 2125.78 -> 1886.02, warm 70.03 -> 72.93, edit 1655.47 -> 1332.32, delete 1687.31 -> 1317.13 ms.

Honors, official events, player award Records, Home and ranking cold timings are mixed. No dedicated optimization is claimed for those paths; their existing lazy calculation, candidate rules, grouping and virtualization are retained. Small warm differences are not meaningful gains. Player Snapshots (~25ms) and monthly award candidates (~90ms per selected season in initial profiling) were left unchanged because speculative rewrites would add correctness risk. Initial JavaScript splitting and PWA cache redesign remain outside scope.

## Cache and memory impact

No new persistent source cache was added. Position placement reads the existing minute cache; News participant/checkpoint indexes are local to one derivation. League prefix WeakMaps contain per-match rating/membership/shot facts for one synchronous History build and are released with its scratch context. Existing arrayItemRevision and bounded weak source caches continue to invalidate all projections after supported source updates. Full payload hashing occurs only in the benchmark, never in application cache lookup. Peak heap/RSS was not measured; no numerical memory improvement is claimed.

## Browser geometry and limits

Run npm run build, then node tests/v264-layout.browser.cjs. Actual headless Chrome uses the built stylesheet and probes element rectangles and elementFromPoint for icons, ratings/stars, names, crests, goal/assist pills, vacancies and button targets at264/320/375/390px. The208-case [layout report](v2.6.4-layout.json) records104 standard/vacancy cases with zero failures and all tested large counters passing at320px and above. Icons remain40px, pitch3:4, rating18px, name16px-high and stats14px-high.

Spare-row exploration removes the avoidable large-counter4-3-3/3-4-3/0-10-0 failures. Remaining10 cases at264px are4-4-2,4-5-1,5-4-1,1-7-2 and1-1-8 with999/9999 on both counters. Four999 pairs require4*67.84375=271.375px within262px; four9999 pairs require308.375px. Both counters remain visible without internal overlap or border clipping, but neighboring information and some9999 hit areas overlap. Those formations already use this layout budget of five physical rows. This is a measured limitation of the chosen group-preserving layout, not a proof of global geometric impossibility. Physical mobile touch-device interaction was not tested.
